# AGENTS.md

Conventions for the Go implementation of Beancount. The yardstick is parity with the official beancount v3 tools (3.2.3) and, for BQL, beanquery 0.2.0, v3's `bean-query`. #562's BQL sub-issues are done; the rest of beanquery's behaviours that differ are in KNOWN_GAPS.md. The deliberate deviations are listed in `queryGaps`: signed zero (#408), `OPEN ON` with a dateless `CLOSE` (#582), RE2 for Python's regular expressions and 64-bit integers that fail on overflow (#589), `GROUP BY` a frozenset failing as it compiles (#636), and opens and closes ordering and grouping by their printed form (#641).

Update this file in the same change whenever you add a package, change the phase pipeline, introduce a convention, or add a compliance suite. A stale convention misleads more than a missing one.

## YAGNI: question first, plan second

Before exploring or planning a feature, establish its value in this project's context (a local dev tool, not a production service): what problem it solves, its measurable impact, and whether that justifies the complexity. When the value is unclear, ask the user; when it is low, say so and propose an alternative or drop it. "Might be useful later" is no justification.

- Compression for the localhost server saves ~3ms per page load: not worth it.
- Line/column positions in parser errors save hours of debugging: worth it.

## Done when

- `gofmt -l .` prints nothing (fix with `gofmt -w <changed-files>`)
- `golangci-lint run` passes
- `go test ./...` and `go test -tags=dev ./...` pass. The former embeds the frontend, so build it first in a fresh clone (`npm ci --prefix assets && npm run --prefix assets build`), or `web`'s tests panic on the missing `web/dist/index.html`. CI runs only the latter, whose `web` serves no frontend; a test of the embedded frontend goes in a `//go:build !dev` file
- A Beancount semantics or query change carries a compliance fixture (see [Beancount compliance](#beancount-compliance))
- A frontend change passes `npm run --prefix assets lint` and `npm run --prefix assets test`

Fuzz with `go test -fuzz=FuzzName -fuzztime=30s ./package`; `make fuzz-promote` copies the `FuzzParser` corpus into `parser/testdata`. Assertions use `github.com/alecthomas/assert/v2`; fuzz targets `defer recover()`.

Before and after performance work, run `go test ./cli -run '^$' -bench CheckScaling`: it checks ledgers of 1k, 4k and 16k transactions, and a scenario whose MB/s falls as the ledger grows has gone quadratic. Micro-benchmarks on a few directives cannot show that.

Library docs: Context7 for third-party dependencies (shopspring/decimal, alecthomas/kong, mattn/go-runewidth); read the source for stdlib and project code.

## Parse → Book → Plugins → Validate → Apply

Each phase owns one job and trusts the one before it. Booking comes before validation because beancount books before Plugins and checks run ([ADR 0003](docs/adr/0003-booking-before-plugins.md)).

| Phase | Does | Leaves to another phase |
|-------|------|-------------------------|
| **Parser** | Parse tokens into AST, report syntax errors and the errors beancount's parser reports on a line under the options read so far (an account root none of the account names in effect, a deprecated pipe, a tag after a posting, an invalid booking method, a posting's cost spec and price errors), keeping their directive | Cross-directive checks, business logic |
| **Booking** | Interpolate missing numbers, match reductions to lots, write booked postings onto the AST, drop transactions that cannot be booked (`ledger/booking.go`, own inventory per account) | Account open/close checks, balance errors, mutating ledger state |
| **Plugins** | Built-in Plugins rewrite the booked directives, in `plugin` directive order, dispatched through `pluginRegistry` (`ledger/plugins.go`) | Validation, mutating ledger state, booking (a transaction a Plugin adds is reported as an `UnbookedTransactionError` and not applied) |
| **Validation** | All semantic checks on booked directives; compute mutation deltas | Booking, mutating ledger state |
| **Apply** | Apply the delta Validate returned, compute derived state | Checking correctness, re-planning bookings |

Validate returns its errors and, independently, a delta or nil; Apply runs whenever there is a delta, errors or not. Like beancount, a directive is reported and still applied unless it cannot be booked, so later directives see it instead of reporting follow-on errors. Booking works one Currency group at a time: a group that cannot be booked is a Dropped group, whose postings leave the transaction while its other groups stay, and a transaction whose postings cannot be sorted into groups is a Dropped transaction, removed from the processed tree. Like beancount's, Booking's errors carry the transaction as written, so their context still lists a Dropped group's postings. See `docs/adr/0002-apply-directives-that-fail-validation.md` and `docs/adr/0004-drop-failed-currency-groups.md`.

## Beancount compliance

Validate every change to semantics, parsing, lexing, formatting, or queries against the matching official tool: `bean-check`, `bean-format`, `bean-doctor`, `bean-query`. Internal refactors and infrastructure changes skip this. CI's test jobs with `compliance-check` set in the matrix (the Linux ones) install beancount 3.2.3 with `pipx` and inject beanquery 0.2.0 into it, so the suites below run there too. Each suite fails on a tool of the wrong version: `bean-check`, `bean-format` and `bean-doctor` must be beancount 3.x, `bean-query` beanquery 0.2. Locally, do as CI does: `pipx install beancount==3.2.3 && pipx inject beancount beanquery==0.2.0 --include-apps`.

**Parity is of intent**: match what the official tool decides, not every byte of how it says or reaches it. A divergence, from a fixture, a probe or the fuzzer, is one of three things:

- **A decision that differs** is a bug to fix: whether a ledger has an error and on which line, whether a directive is kept, applied or dropped, which numbers, costs and lots are booked, and what `format` and `query` print. These are held exactly (lines and exit status for `check`, bytes for `format` and `query`).
- **Wording** follows beancount's sentence and stops at Python's artifacts. A `check` message may say what beancount says (`Could not resolve units currency`), since a user searching for the text finds beancount's documentation. It never carries what only Python's runtime puts there: an exception's name or text (`ValueError: …`), a traceback, the repr of an object (`KeyValue(key=…)`, `Decimal('1')`, `<class '…MISSING'>`), or a Decimal's exponent (`-10.0000000000000000000000000 USD` for `-10 USD`). Quote an amount as it is written, and a computed number without trailing zeros. A message that already differs is not a bug: no suite compares wording, and no ticket is filed for it. The two exceptions are an option's message (`config`) and a `query` error, which is beanquery's own text.
- **An accident of beancount's implementation** is recorded, not reproduced: a crash with a Python exception, a result that depends on Python's hash order, or a lexer quirk that rejects a ledger no user would call wrong (#704). Answer sensibly, and list it under "Deliberate deviations" in `KNOWN_GAPS.md` with the issue that decided it.

A ticket quotes the official tool's output as evidence of the decision, never as the text to produce. When it is unclear which of the three a divergence is, ask.

**Ledger semantics**: `cli/compliance_test.go` runs every `testdata/compliance/<name>.pass.beancount` / `.fail.beancount` through both implementations whenever `bean-check` is on PATH (`go test ./cli -run 'Compliance|Official'`) and, for `.fail` fixtures, compares the lines errors are reported on (`path:line:`, ignoring our column) with `bean-check --json`'s, in `check`'s text and `--json` output alike; a `.pass` fixture's `--json` output must match byte for byte. Most messages are worded apart, so `--json` is held to filenames and lines, not bytes. A fixture whose lines differ on purpose or through an open issue goes in `lineGaps` with the reason. A `gap_` fixture is one we do not satisfy yet: the in-process suite skips it, and the differential still checks its expectation against `bean-check`. Record known divergences in `testdata/compliance/KNOWN_GAPS.md`. An `applied_` fixture holds one directive that is reported but still applied; `TestNoFollowOnErrors` checks that both implementations report exactly that one error, which exit codes cannot show.

**Queries**: `cli/query_compliance_test.go` runs every `testdata/compliance/query/*.bql` through both implementations in text and csv (`go test ./cli -run 'QueryFixtures|OfficialQueryParity'`). It compares stdout byte for byte and the exit status. When beanquery fails a statement, it also compares stderr. One-shot `bean-query` prints a Python traceback there, so the suite takes the text of beanquery's interactive shell from a Python script run on bean-query's interpreter (`beanqueryShellError`). The `query` row below gives the error format. Name prefixes: `err_` expects such an error from us, `numberify_` adds `-m`. A fixture that differs goes in `queryGaps` with the issue that closes it or, for a deliberate deviation, the issue that decided it and why. `query/run_test.go` pins every `err_` fixture's `Error.Report` and runs it through `Run`; a new `err_` fixture adds its report there, probed with beanquery's shell.

**Format**: `TestOfficialFormatParity` in `cli/compliance_test.go` formats every `testdata/compliance/format/*.beancount` and compares the output **byte-for-byte** with `bean-format`'s (`go test ./cli -run FormatParity`). A fixture that differs through an open issue goes in `formatGaps` with the reason and the issue.

**Doctor**: `cli/doctor_test.go` runs every `testdata/compliance/missing_open/*.beancount` through `beancount doctor missing_open` and, whenever `bean-doctor` is on PATH, compares stdout **byte-for-byte** with `bean-doctor missing_open` (`go test ./cli -run MissingOpen`). An include target goes in a subdirectory, so it is not a fixture itself. A fixture that differs through an open issue goes in `missingOpenGaps` with the reason and the issue.

**Differential fuzzer**: `TestDiffFuzz` in `cli/difffuzz_test.go`, behind the `difffuzz` build tag and so in no other suite or CI job, finds divergences no fixture covers (`go test -tags=difffuzz ./cli -run DiffFuzz -difffuzz.time=5m -timeout=0`; `.golangci.yml` sets the tag, so lint is what compiles it in CI). It runs every compliance fixture and fuzz corpus entry, then mutations of them, through our `check`, `format` and `query` and through the official tools, held to what the suites above compare: the lines errors are on and whether check fails, format's bytes on a ledger ours parses, and what a few fixed statements print and whether they fail (`fuzzQueries`). One Python process stands for the official tools (`cli/testdata/difffuzz_oracle.py`, on bean-query's interpreter); a ledger they raise on is skipped. It minimizes a diverging ledger by lines, confirms it with the tool itself, and writes it with both outputs to `.difffuzz/` (git-ignored), once per signature: the differing output lines without names and numbers. A mutation is reported only for a command its seed agrees on. A divergence that is deliberate or has an issue goes in `knownDivergences` with the reason, and is then counted, not written; each other one is triaged as above (a decision that differs becomes an issue and, once fixed, a fixture; wording never does).

**Gap maps stay live**: `lineGaps`, `formatGaps`, `queryGaps` and `missingOpenGaps` skip only the comparison with the official tool. An entry whose fixture agrees again, or that names no fixture, fails its suite, so closing a gap removes its entry.

**Pin first, implement second**: bean-query is full of undocumented quirks (column names from the source text like `SUM((position))`, centred and truncated headers, padded number cells in CSV, a sign column in every amount, per-currency precision, implicit GROUP BY). Probe the official tool with a small ledger and match the observed bytes:

```bash
bean-query testdata/compliance/query/ledger.beancount "select account, sum(position) group by account"
bean-query -f csv ledger.beancount "select 1 + 2"   # csv shows untruncated headers
bean-query ledger.beancount "help targets"           # official column/function reference
diff <(go run ./cmd/beancount query f.beancount "$Q") <(bean-query f.beancount "$Q")

bean-doctor lex f.beancount; beancount doctor lex f.beancount  # token models differ; compare by eye
diff <(bean-format f.beancount) <(beancount format f.beancount)
beancount format f.beancount | bean-check /dev/stdin  # round-trip
```

## Key patterns

**Registry dispatch**: dispatch by kind through registry maps, never switch statements. Ledger directives go through `handlerRegistry` in `ledger/handlers.go` (`DirectiveKind` → `handler` with `validate`/`apply`); handlers call the functions in `validation.go` directly, so there is exactly one registry. Build validators with `newValidator(l.accounts, l.opens, l.config)`, the stable read-only map and the `openIndex` of the opens wherever the ledger dates them (each account's first open, and the currencies of its last open naming any, which like beancount's constrain every posting to it), rather than a copy from `Accounts()`. Query columns, functions, aggregates, operators and the attributes of structured types follow the same rule (`query/env.go`, `functions.go`, `aggregates.go`, `operators.go`, `attributes.go`).

**Owner computes**: the type that owns the data computes on it; coordinators call owner methods and aggregate. The booker calls `inventory.book` and `inventory.augment` instead of matching lots itself, and the query package's `cost()`, `value()` and `convert()` call `Position.AtCost`, `Ledger.MarketValue` and `Ledger.Convert` instead of looking up prices.

**Lexer newline ownership**: every content-bearing token (including COMMENT) consumes its trailing newline; NEWLINE tokens stand only for blank lines, emitted solely by `scanNextToken()`. `parseComment` strips the newline from the comment's content. Consistent ownership keeps the formatter idempotent around consecutive blank lines and comments.

**State as receiver**: validators and processors keep config and lookups on the struct and read them through the receiver.

**Constructors take the directive**: `newAccountNotClosedError(close *ast.Close)` extracts date, account and position itself.

**Context and telemetry**: public functions doing I/O or processing take `context.Context` first, check `ctx.Done()` in long loops, and time work with `telemetry.FromContext(ctx).Start("package.operation <context>")` (e.g. `parser.lexing`, `loader.parse main.beancount`).

**Errors**: wrap I/O errors with context (`fmt.Errorf("failed to read %s: %w", filename, err)`); return parser errors as-is (they carry positions); collect ledger errors into slices as `*ledger.Diagnostic` values (kind, message, directive, position, account), built by a `new…Error` constructor per kind; add a Go type only where a caller matches on it with `errors.As` (`BalanceMismatchError`). Every error a loaded ledger reports on a line has one shape, `diagnostic.Positioned`: `Kind()` (the `type` the web API sends), `Message()` (the text without its Error line) and `GetPosition()`, its severity read with `diagnostic.SeverityOf`; `Error()` is the Error line, `": "` and the message. A new positioned error gets the three methods (`ast`'s structurally, since it cannot import `diagnostic`), not a `MarshalJSON`. Kind, message and position are read from the shape, never from a trimmed `Error()`: `check --json` writes `Message()` and the position, and the web API builds its JSON in one place (`jsonSafeSourceError`; only `ledger.Diagnostic` marshals itself, to add `account` and `date`), leaving `LoadError` for an error without the shape, such as an I/O failure. The CLI renders any error with `GetDirective()` with the directive under it, a transaction's postings as booked like bean-check's (`cli/errors.go`), or alone when it returns nil (an error beancount raises with no entry, such as an `InterpolationError`, is built without its directive: `Diagnostic.entryless`), and any other positioned error with the source lines of the file its position names, looked up in `ledgerload.Result.Sources`, or with none when it does not have that file; the renderer of a loaded ledger's errors is built in one place (`newLedgerErrorRenderer`), and a load that cannot go on is reported by one helper (`printLoadFailure`, in each command's layout). A `check` message is worded here, not copied from bean-check ([Parity is of intent](#beancount-compliance), #518).

**Performance**: `strings.Builder` for concatenation, `sync.Pool` for frequently allocated maps, capacity hints when the size is known.

## Package conventions

| Package | Key rules |
|---------|-----------|
| **ast** | All AST node types, `Directive` interface. Builders use functional options. `Document.ResolvedPath` is the one place a document's path is resolved: the validator's message and the printer both read it. |
| **parser** | Parsing only, returns `*ast.AST`. Types live in `ast`. Like beancount's grammar, which matches its account pattern at the start only, an account is valid once its second component starts with an uppercase letter or a digit; past that only the lexer's rule applies (`ast.LexesAccount`, which `lexerRejectsAccount` uses too). An account word the lexer rejects (`Assets:bank`) is an invalid token, which drops the directive it is in. Like beancount's parser, the parser holds the options in effect (`Parser.options`, a `config.Config` it applies each option to as it reads it, `Config.ApplyOption`, starting from the defaults in each file, as beancount parses each file on its own): an account the account pattern rejects, or whose root is none of the five account names in effect on its line, is reported on every line that writes it (directives, postings, metadata and custom values) and kept; the ledger checks no root. Such an error that keeps its directive is a `ParseError` with `Kept` set (`MustParse*` panic only on one that drops a directive), as is a deprecated pipe among a transaction's strings (`"Payee" | "Narration"`), reported where the strings start unless `allow_pipe_separator` is in effect. So is an open naming a booking method beancount does not know, which the parser gives the `booking_method` option in effect on its line in its own file, as beancount's open rule does. So is a tag or link line after a transaction's first posting, whose tags and links are ignored; the line is a `TransactionBodyItem.TagsLinks`, for the formatter only. So are the errors beancount's grammar raises as it reads a posting (`parser/posting_errors.go`): its cost spec's once the braces close (a merge marker, each component the spec repeats, kept in `Cost.Duplicates` while the first of each kind counts, a compound inside total braces) and its line's once the line ends (a negative price, a total price without units, a price in another currency than the cost), so they stay reported when a later syntax error drops the transaction. Like beancount, a syntax error drops the directive it is in and parsing resumes at the next line in column 1, or, as Bison retries each token after the error, at an earlier token that can start a declaration (a date, `option`, `include`, `plugin`, `pushtag`, `poptag`, `pushmeta`, `popmeta`): the one that raised the error, one later on its line, or one on an indented line: `Parse` returns the partial AST with a `ParseErrors` listing each one (and, in `AST.DroppedAmounts`, the amounts the dropped directives read before their error, which the ledger's display context counts, as beancount's parser feeds its display context with each amount it reads; the loader merges them across includes), and, as beancount's lexer reports every invalid token, each invalid token the recovery skips (one beancount's grammar alone rejects, such as a lone sign or an unmatched parenthesis, is not reported; a one-letter key such as `a:` is invalid). Like beancount's Bison parser, a grammar error is reported only once three tokens have been shifted since the last error, reported or not (`Parser.shiftedSince`: a line break and an indent count as tokens, a comment does not); an invalid token is always reported. Like beancount's lexer, the lexer fails on no input: a comment may hold any bytes, a string holding invalid UTF-8 is an error on the line the string ends on, and invalid UTF-8 or a control character elsewhere is an invalid token up to the next whitespace. Like beancount's catch-all rule, any invalid token runs to the next whitespace, a quote in it included (`invalidToken`); a quote opens a string only when its closing quote is found before a backslash ending a line (`closingQuoteAhead`), and a lowercase word that is no keyword or key lexes as the keyword starting it, if any, then an invalid token (`closed` is `close`, `d`). An invalid token starting the line right after a dated directive drops that directive, as Bison discards it while it waits to see whether the directive goes on; a blank or comment line between keeps it. A dated directive's header, a posting and an undated line (`option`, `plugin`, `include`, …) end at their line (`finishHeader` checks the token lines, since tokens own their newline): one continued on the next line, or metadata on its own line, is a syntax error, since beancount has no inline metadata. A blank or whitespace-only line ends a directive's body, so an indented line after one is a syntax error, as in beancount. Like beancount's INDENT, a line's leading whitespace is an indent only when it is spaces and tabs alone (`Parser.indented`, never `Column > 1`): a lone `\r` in it makes the line start in column 1. A string spanning lines moves that end to the line it closes on, where a comment is the inline comment; the parser finds that line with the lexer's own line count (`Parser.endLine`, `ast.CountLineBreaks`), which, like beancount's, breaks lines only at `\n` (`\r\n` included) and reads a lone `\r` as whitespace; `ast.SplitSourceLines` splits source text the same way for every reader of positions. |
| **formatter** | Renders the AST, held to bean-format's line pattern (`beancount/scripts/format.py`): it aligns only a plainly spelled number, or two joined by one operator in parentheses (`(1 + 2)`), followed by a currency, and copies every line bean-format leaves alone (headers, comments, blank and metadata lines, unaligned postings) from the source. It always formats a source, with no mode for rendering directives without one (that is the printer's job); a `Formatter` holds options only, and a Format call's state lives on its `run`. Two modules make the decisions, so a per-kind printer holds no source-line heuristics of its own: the `sourceView` (`source.go`) answers with one rule whether an item owns its source line (no other top-level item starts on it and the item starts it; the item runs up to the next node, so a string spanning lines hands it those lines too), and the pure line-pattern function (`layout` in `pattern.go`) reads an owned line with bean-format's own regular expressions (its line pattern, beancount's `ACCOUNT_RE` and `CURRENCY_RE`) and returns a `lineLayout`: align, with prefix, number, the rest of the line from the currency on as written, and widths; copy (a line that does not align, re-indented to the posting indent when it starts with an indented account); or unowned. The posting indent is the most frequent indent of the posting lines that pattern re-indents. No per-kind printer rebuilds a line from the AST: an item that does not own its source line takes the one fallback (`run.fail`), and `Format` returns an error naming the item's position and writes nothing, so the source must be the text the AST was parsed from. Every width it aligns by (prefix, number, padding) counts code points, as bean-format's `len()` and `str.format` do, not display columns. Limits are in `KNOWN_GAPS.md`. |
| **printer** | Renders directives as beancount 3.2.3's `printer.py` does, byte for byte (`print_*` query fixtures; its known differences are in KNOWN_GAPS.md): numbers as parsed, a transaction's postings aligned on their currency and indented two spaces, printer.py's fixed columns for open, balance and price, a balance's tolerance whenever one is written (`~ 0` included), a note's and a document's tags then links each after a space, a document's path resolved against its file's directory, as beancount holds it, metadata lines except keys starting with `__` (`__implicit_prices__`), no source comments. `Print` follows `print_entries`' blank-line policy; `Sprint` renders one directive (`format_entry`). `WithBookedPositions(Ledger.BookedPositions)` prints a posting as its booked postings, `WithBalanceDiffs` a failed assertion's difference. Query PRINT, `import`, `doctor missing_open` and the CLI's error context print through it. |
| **ledger** | Its exports are its interface: a name, method or field is exported only when another package uses it or an exported signature needs it. `decimal.Decimal` for amounts. Booking methods: `STRICT` (default), `STRICT_WITH_SIZE` (as `STRICT`, and when that cannot choose among several lots, the oldest lot of the reduction's size), `NONE`, `FIFO`, `LIFO`, `HIFO`, `AVERAGE` (like beancount, every reduction under it fails, and a merge cost `{*}`, which the parser reports, is booked like `{}`); the parser reports an open naming any other method and gives it the `booking_method` option in effect on its line. Like beancount's parser, Booking fixes up a compound cost inside total braces (`{{5 # 3 USD}}`, booked with its per-unit number ignored), a negative price and a total price without units before booking, which the parser reports, and books total braces without an amount (`{{}}`, `{{2020-01-01}}`) as the per-unit cost they amount to; `inventory.book` decides augment vs. reduce (beancount's `is_reduced_by`), reports which, and books a reduction at once, matched like beancount's against the lots at cost of either sign (STRICT weighs them all; the other methods book only those of the opposite sign), in its Currency group's scratch inventory, a copy made only for a reduction (`reducedBy` decides from per-sign lot counts, so a ledger that only adds lots stays linear); `inventory.augment` adds every other posting, with its cost per unit and dated, once interpolation has completed it and the transaction is booked. The booker only groups, stages, rolls back a Dropped group, commits what the interpolation module returns and augments the inventories. Interpolation (`ledger/interpolation.go`) completes one Currency group: given the group, the positions its reductions booked and the transaction's spec tolerances, `interpolate` returns each posting's completed amount, cost and price, whether it is left out, the amounts the amount-less posting is booked at, and the group's residuals, or the errors that make it a Dropped group (more than one missing number, decided once in `tooManyMissing`, or a missing number the residual does not determine); the booker expands the amount-less posting into one posting per group, since that spans groups. Booking publishes one record per booked posting of an Applied transaction, `Ledger.BookedPositions`: a `BookedPosition` per lot a reduction was booked against, otherwise one of its own, with signed units, a per-unit `BookedCost` (number at the precision Booking holds it, currency, lot date defaulting to the transaction's unless its units were interpolated, label) and `Reduced` (beancount's `Booking.REDUCED`); a Dropped group's postings have none. Apply replays the record, and Plugins, the query package and the printer read it rather than re-deriving lots or costs from the cost spec. `tolerances` (`ledger/tolerance.go`), built once per `Process` from the tolerance options and the only reader of them, answers every tolerance question: a transaction's tolerance per currency before booking (`spec`, which rounds interpolated numbers: the coarsest its numbers imply, or the finest under `use_precise_interpolation`, with a currency's default counting only when a posting names the currency) and once booked (`booked`, for the residual check), and a balance assertion's (`balance`); the booker holds it, and the Balance handler asks it for an assertion's tolerance before padding (`pads.fill`) and checking (`checkBalance`) the assertion. `priceIndex` (`ledger/prices.go`) answers `GetPrice`: a pair's latest rate on or before the date, from its own prices or the inverses of the other direction's, never through a third currency; a zero price has no inverse. The ledger owns Valuation (`ledger/valuation.go`): `Position.AtCost`, `MarketValue`, `Convert` and `ConvertAmount` value a position on a date, and the query package's `cost()`, `value()` and `convert()` call them. `GetBalanceTree` (`ledger/balance_tree.go`) builds from the accounts, every one opened or posted to (like beancount, a posting to an account never opened is reported and still applied, so the account counts, with no open date), and the configured account-type names alone, stating each account's balance under a `Valuation` (At cost by default): it sums the `BookedPositions` of the account's postings in the period per lot and values them once, on the end date or else today. With `closed` it returns Closed balances, a balance sheet's as of a date: Equity gains Current earnings (the Income and Expenses positions through the date) and Current conversions (the negated cost balance of every posting) in the accounts `Config.CurrentAccounts()` names, summed in beancount's order so that 28-digit rounding gives its amounts every time (Current earnings account by account in account order, Current conversions per lot in the order the postings were applied, then each lot's cost), and, At market value or Converted to a currency, `Equity:Earnings:Unrealized`, whatever leaves the valued sheet off zero; a computed amount merges into a real account of its name, and one that comes out empty is left out. `Process` leaves the tree it is given as it was and returns the Processed tree, built from a copy of the directive list and of every transaction, note and document it writes to (and of any directive that repeats a metadata key: like beancount's parser, a transaction and a posting keep a key's first value and report each other one that is not the same Python object (`sameObject`), any other directive its last value in the key's first place, `ledger/metadata.go`); whatever the ledger keys by pointer (`BookedPositions`, a `Diagnostic`'s directive, balance differences) names its nodes, so every reader takes the tree `Process` returns. Its error is only a failure to process at all (a cancelled context, or directives that cannot be sorted); diagnostics, errors and warnings alike, come from `Diagnostics()` (`Errors()` for the errors), and `Config()` holds the options it processed under. Apply leaves booked postings in the Processed tree's `txn.Postings`, in beancount's booked order (by Currency group, sorted into groups in `ledger/groups.go` like beancount's `categorize_by_currency`, after which, as `replace_currencies` does, units and a price that leave out their currency take the ones categorizing resolved (only a posting of an account alone is an auto-posting: one with a cost or a price but no units, a total price Booking drops included, leaves out its units currency too) and a cost that leaves out its currency takes its group's, with or without its number, so a reduction at `{}` or `{"label"}` matches only the lots held in it; an amount-less posting becomes one posting per group with a residual); `BodyItems` keeps the source layout for the formatter. Like beancount's, a balance assertion and the padding that fills it see the account's whole subtree (`Ledger.subtree`): `balance Assets:Bank` counts `Assets:Bank:Checking`, opened or not. The pads module (`ledger/pad.go`) owns padding: `pads.fill` decides whether a balance assertion's pad fills it and builds the padding transaction, and the Balance handler's Apply consumes the pad and applies the padding unbooked, its units as they are and without cost, as beancount's pad plugin inserts it after booking. A padding transaction is dated and positioned at its pad and carries its metadata; its postings carry the balance assertion's position and metadata, like beancount's. |
| **loader** | Recursive includes, deduplicated by absolute path; a repeated include is loaded once and reported as a load error (beancount's "Duplicate filename parsed"). Like beancount, only the top-level file's options and `plugin` directives count; an included file's are dropped, after its options are checked (`config.CheckOption`): an invalid one is a load error on the included file's line, a valid one a warning. Every include is expanded like Python's `glob.glob(recursive=True)`: `**` spans directories, wildcards skip dotfiles, and an unmatched glob, including a missing plain path, is a load error. Non-fatal issues go to `LoadResult.Diagnostics`; with `WithSyntaxRecovery` (which `ledgerload` uses) so do syntax errors, while `format` fails on the first one that drops a directive and leaves out those that keep it (`ParseError.Kept`). `Load(ctx, Source)` is the one entry: the file at `Path`, or `Data` standing for it, its positions carrying `Name` (else `Path`), every option applying alike. `Stdin(data)` is a ledger on stdin as `bean-check /dev/stdin` reads it: the file `/dev/stdin`, so its relative includes and documents roots resolve against `/dev`, with `<stdin>` in its positions. |
| **ledgerload** | The one way the commands, `web` and the parity harnesses load a ledger: `Load(ctx, loader.Source)` follows includes, discovers documents and recovers from syntax errors, then processes, and returns the Processed tree, the `Ledger`, the load diagnostics, and `Root`, `Includes` and `Sources`; its error is a load that cannot go on. `Result.Diagnostics()` is everything the ledger reports as one new list, the load diagnostics then the ledger's, for a caller that reports both alike (`check --json`, `web`); one that renders them apart (`check`, `query`) reads `LoadDiagnostics` and `Ledger.Diagnostics()`. `Result.With` processes the loaded tree again with directives added, in a new `Ledger`, without loading again (`import`'s Extracted directives). Outside tests, nothing else calls `Ledger.Process`. |
| **cli** | A command loads through `ledgerload.Load(ctx, FileOrStdin.Source())` and only decides how to print what it returns, where the official tools' differences belong: `check` prints warnings and errors with source context, `query` errors plain (`loadQueryContext`, which `runOurQuery` calls too, so the parity suite runs the command's loading path), `doctor` nothing. `format` only loads, with `loader.New().Load`. |
| **config** | Beancount option parsing into typed configuration. Like bean-check, options apply one by one (`ApplyOption`, which the parser also calls as it reads each option): the last valid scalar value wins, and an unknown name or invalid value is a positioned error that leaves the other options in effect (`ParseOptions`). An option written under a name beancount renamed (`renamedOptions`) is reported as renamed and still applied, under its current name; a deprecated one (`deprecatedOptions`) is reported whatever its value. An option's number is read as beancount's `D()` reads it (`parseNumber`: empty is 0, commas and spaces dropped, then `pydecimal.NewFromString`). An invalid value carries beancount's message where its converter words one; beancount's capitalised messages are a `beancountError`, which the error-string lint allows. |
| **query/bql** | BQL lexer + recursive-descent parser, syntax only, held to the parser's rules: zero-copy tokens, positioned errors, fuzz test. Every node records its `Span`, the byte offsets of its source text, which names an unaliased target (`Target.Text`) as in beanquery. Like beanquery's grammar, SELECT's FROM tries a Table reference (`bql.Table`: `#name`, `#` alone, or a quoted name) before a FROM filter, and only the clauses after FROM may follow one; PRINT's, BALANCES' and JOURNAL's FROM take a FROM filter only. |
| **query** | `Run` is the interface: BQL text, a `Context` (Ledger, Config and the processed tree, which Run requires), a `Format` and numberify in; beanquery's bytes out (nothing for an empty text result, or for a text with no statement, which its shell skips: an empty one, or one opening with `;` or `(`). For a statement that does not parse or compile, or fails while it runs (an invalid regular expression or `subst()` replacement, which reads its replacement as Python's `re.sub` does (`query/template.go`), an integer overflow, a LIMIT beyond int64: `fail` panics with an `evalError` that `Run` recovers), `Run` writes nothing and returns an `*Error` with beanquery's message. `Error.Report` renders it as beanquery's interactive shell prints it: `error: ` and the message, the statement's lines up to the error's node behind `| `, and a caret under each character of the node (its `bql` span). A parse error is `syntax error` with one caret. An error beanquery raises without a node is the `error: ` line alone (KNOWN_GAPS.md). The CLI prints the report on stderr and exits 1; the web API returns it as output. `Run`, `Context`, `Format` and `Error` are the whole exported API; the stages behind it are unexported, and the package's own tests (all `package query`) reach them directly. Inside, parse → compile → execute → render: compiler resolves names and types with beanquery-parity error messages (a function by its name as written: the parser lowercases an unquoted one and keeps a quoted one; a double-quoted string (`bql.Str.DoubleQuoted`) as the column of the current table its value names, like beanquery's `_constant`, GROUP BY and ORDER BY matching it to that column's target through `exprKey`), and type-checks operators against `operators` (`query/operators.go`, beanquery's `OPERATORS`): an operand pair must match a signature exactly, after an untyped (object) operand is cast to the other's type (`casts`, beanquery's `types.MAP`); AND, OR, IN and NOT IN take any types (`untypedOperators`); BETWEEN's three operands must all be numbers, dates or strings (`betweenGroups`); NOT and unary minus look up `unaryOperators`, and a function call its overloads in `functions`, like beanquery's `function_lookup` (`lookupSignature`): each combination of the arguments' bases in turn, a bool's being bool then int, as Python's bool subclasses int, so a bool overload wins and an int one takes a bool as its int value (`asBase`); a typed operator on a NULL operand gives NULL; executor reads `Context.AST` (interpolated amounts) read-only and maps `Ledger.BookedPositions` to its positions for the position, cost and weight columns rather than re-deriving booking (FROM's summarization records the positions of the postings it creates); the `meta` columns are Python dicts built from a directive's or a posting's position and metadata (`query/meta.go`: filename, lineno, the metadata, and a posting's `__automatic__` when Booking interpolated one of its numbers, `ast.Posting.Automatic`), the only values a subscript takes; `entry` is beanquery's Transaction structure, its attributes in `attributes.go`, and printed as Python's repr of it from `Ledger.BookedPositions`; a SELECT reads a Table, an `environment` (`query/env.go`: its columns, the columns `SELECT *` expands to, and its rows), which its other clauses compile against: `postings` unless its FROM names another, `entries`, the Empty table (`#`), or one of beanquery's Tables of directives in `query/tables.go` (`transactions`, `prices`, `events`, `notes`, `documents`, `balances`, one row per directive of a kind, `commodities`, one per currency, and `accounts`, one per account opened or closed, whose `open` and `close` structures hold the `*ast.Open` and `*ast.Close`; a note's and a document's tags and links are `tFrozenset`, beanquery's raw `frozenset` type, which no function takes; a row a directive does not make up alone carries the rest as its `evalRow.Record`); `tables` holds them by name; like beanquery's `_compile_from`, a Table reference names a Table, and so does a FROM filter that is a lone name of one but not of a postings column, OPEN, CLOSE and CLEAR after it ignored; `meta()`, `entry_meta()`, `any_meta()` and `has_account()` compile as beanquery rewrites them, through the current Table's columns (`columnRewrites`), so they fail on a Table without them; SELECT (which BALANCES and JOURNAL desugar to) and PRINT share one FROM compile (`compileFrom`) and its OPEN, CLOSE and CLEAR transforms; like beanquery, a SELECT's FROM expression compiles over the postings table and joins WHERE as one filter on posting rows (`EvalAnd([c_from_expr, c_where])`), while PRINT's compiles over entries and keeps directives (`compiledFrom.entries`); PRINT hands what its FROM reads to the printer with `Ledger.BookedPositions`; HAVING compiles to a hidden aggregate target; like beanquery, a grouped query's targets outside the group key (HAVING's, an ORDER BY expression's) read their non-aggregate parts from the last scanned row; PIVOT BY reshapes the executed table after ORDER BY and LIMIT (`table.pivot`, beanquery's `EvalPivot`); ORDER BY, `min()`, `max()` and PIVOT BY order values as Python orders beancount's (`order.go`: `Position.sortkey` through `ledger.SortKey`, the one implementation, which also orders the ledger's inventories and residuals, amounts by currency, inventories by sorted positions, sets by inclusion, lists (list constants and `other_accounts`, a set-typed column holding a sorted `listValue`) element by element); the executor evaluates a row's targets where WHERE keeps it, and `balance` is lazy (`evalRow.balanceValue`), as in beanquery; numberify splits amount columns before either format renders; renderers reproduce beanquery's per-type layout byte-for-byte, quantizing amounts with `Ledger.DisplayContext` (source precisions, fixed by `display_precision`). |

## Frontend (assets/)

Vite + Solid + TypeScript, styled with Tailwind CSS 4 + DaisyUI, built into `web/dist/` and embedded in the Go binary. `web/assets.go` injects metadata (version, commitSHA, readOnly, watching, and the ledger's title) into `index.html` on each request; the dev server injects dummy values via a Vite plugin. `npm run --prefix assets dev` proxies `/api` to `:8080`.

**Dependencies**: change them only through `npm install --prefix assets <pkg>` / `npm uninstall --prefix assets <pkg>`, so `package.json` and the lockfile stay in sync.

**CodeMirror**: import individual `@codemirror/{state,view,commands,language,lint,autocomplete}` packages, theme with `EditorView.theme()` and `--color-` CSS variables, and bind only `indentWithTab`. This keeps the editor ~75KB gzipped, against 400KB+ for `basicSetup` or wrapper packages that defeat tree-shaking.

**Composition**: build shared UI as small Radix-style primitives. Routes own data fetching, state branching, and page layout, and compose the primitives so intent stays visible:

```tsx
<FinancialReport.Root>
  <FinancialReport.Grid>
    <FinancialReport.Column>
      <FinancialReport.Table section={assets} currencies={currencies} />
    </FinancialReport.Column>
  </FinancialReport.Grid>
</FinancialReport.Root>

const sections = () => FinancialReport.getSections(data()?.roots, ["Assets"])
```

**Ledger errors**: `assets/src/lib/errors.ts` holds one store of the ledger's errors (from `GET /api/source`) for every page: the sidebar's "Errors (N)" and the `/errors` page read it, and it refetches after a save and on each live reload (`hooks/useReloadEvents.ts`, the server's reload events, which `useFileChange` reads too). A link to a line is the editor's `?file=` (the root or one of its includes) and `?line=`.

Playwright e2e tests live in `assets/tests/`.
