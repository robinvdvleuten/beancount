# Coding standards

The patterns code in this repository follows, applied in review. For each package a diff touches, also apply its rules in `docs/packages/<package path>.md`.

**Registry dispatch**: dispatch by kind through registry maps, never switch statements. Ledger directives go through `handlerRegistry` in `ledger/handlers.go` (`DirectiveKind` → `handler` with `validate`/`apply`); handlers call the functions in `validation.go` directly, so there is exactly one registry. Build validators with `newValidator(l.accounts, l.opens, l.config)`, the stable read-only map and the `openIndex` of the opens wherever the ledger dates them (each account's first open, and the currencies of its last open naming any, which like beancount's constrain every posting to it), rather than a copy from `Accounts()`. Query columns, functions, aggregates, operators and the attributes of structured types follow the same rule (`query/env.go`, `functions.go`, `aggregates.go`, `operators.go`, `attributes.go`).

**Owner computes**: the type that owns the data computes on it; coordinators call owner methods and aggregate. The booker calls `inventory.book` and `inventory.augment` instead of matching lots itself, and the query package's `cost()`, `value()` and `convert()` call `Position.AtCost`, `Ledger.MarketValue` and `Ledger.Convert` instead of looking up prices.

**State as receiver**: validators and processors keep config and lookups on the struct and read them through the receiver.

**Constructors take the directive**: `newAccountNotClosedError(close *ast.Close)` extracts date, account and position itself.

**Context and telemetry**: public functions doing I/O or processing take `context.Context` first, check `ctx.Done()` in long loops, and time work with `telemetry.FromContext(ctx).Start("package.operation <context>")` (e.g. `parser.lexing`, `loader.parse main.beancount`).

**Errors**: wrap I/O errors with context (`fmt.Errorf("failed to read %s: %w", filename, err)`); return parser errors as-is (they carry positions); collect ledger errors into slices as `*ledger.Diagnostic` values (kind, message, directive, position, account), built by a `new…Error` constructor per kind; add a Go type only where a caller matches on it with `errors.As` (`BalanceMismatchError`). Every error a loaded ledger reports on a line has one shape, `diagnostic.Positioned`: `Kind()` (the `type` the web API sends), `Message()` (the text without its Error line) and `GetPosition()`, its severity read with `diagnostic.SeverityOf`; `Error()` is the Error line, `": "` and the message. A new positioned error gets the three methods (`ast`'s structurally, since it cannot import `diagnostic`), not a `MarshalJSON`. Kind, message and position are read from the shape, never from a trimmed `Error()`: `check --json` writes `Message()` and the position, and the web API builds its JSON in one place (`jsonSafeSourceError`; only `ledger.Diagnostic` marshals itself, to add `account` and `date`), leaving `LoadError` for an error without the shape, such as an I/O failure. The CLI renders any error with `GetDirective()` with the directive under it, a transaction's postings as booked like bean-check's (`cli/errors.go`), or alone when it returns nil (an error beancount raises with no entry, such as an `InterpolationError`, is built without its directive: `Diagnostic.entryless`), and any other positioned error with the source lines of the file its position names, looked up in `ledgerload.Result.Sources`, or with none when it does not have that file; the renderer of a loaded ledger's errors is built in one place (`newLedgerErrorRenderer`), and a load that cannot go on is reported by one helper (`printLoadFailure`, in each command's layout). A `check` message is worded here, not copied from bean-check ([Parity is of intent](AGENTS.md#beancount-compliance), #518).

**Performance**: `strings.Builder` for concatenation, `sync.Pool` for frequently allocated maps, capacity hints when the size is known.

**Dependency behaviour lives in a test**: when code relies on how a dependency behaves, pin that behaviour in a test that fails when the dependency changes, as `TestZero` pins `pydecimal.Zero`'s exponent; comments and docs state what our code does. Prose about a dependency goes stale without a sound: AGENTS.md still said shopspring's `decimal.Zero` had exponent 1 after v1.5.0 changed it to 0.
