# `parser`

Parsing only, returns `*ast.AST`. Types live in `ast`. Like beancount's lexer, with flex's longest match, the lexer reads at the start of a word what its rules read there: an account as far as its pattern goes (`ast.AccountLexLen`: a type, then one or more `:` and a name, a non-ASCII character admitted anywhere, so `Expenses:B:` is the account and a colon and `Assets:X_y` the account and an invalid token), else a capital letter before whitespace, else a currency (`USDnarration:` is a currency, a key and a colon), else an invalid token up to the next whitespace, a quote in it included (`Assets:bank`, `A:`, `USDa:`'s `a:`, `☕"y"`), which drops the directive it is in. Like beancount's grammar, which matches its account pattern at the start only, an account is valid once its second component starts with an uppercase letter or a digit; past that only the lexer's rule applies (`ast.AccountLexLen`). Like beancount's parser, the parser holds the options in effect (`Parser.options`, a `config.Config` it applies each option to as it reads it, `Config.ApplyOption`, starting from the defaults in each file, as beancount parses each file on its own): an account the account pattern rejects, or whose root is none of the five account names in effect on its line, is reported on every line that writes it (directives, postings, metadata and custom values) and kept; the ledger checks no root. Such an error that keeps its directive is a `ParseError` with `Kept` set (`MustParse*` panic only on one that drops a directive), as is a deprecated pipe among a transaction's strings (`"Payee" | "Narration"`), reported where the strings start unless `allow_pipe_separator` is in effect. So is an open naming a booking method beancount does not know, which the parser gives the `booking_method` option in effect on its line in its own file, as beancount's open rule does. So is a tag or link line after a transaction's first posting, whose tags and links are ignored; the line is a `TransactionBodyItem.TagsLinks`, for the formatter only. So are the errors beancount's grammar raises as it reads a posting (`parser/posting_errors.go`): its cost spec's once the braces close (a merge marker, each component the spec repeats, kept in `Cost.Duplicates` while the first of each kind counts, a compound inside total braces) and its line's once the line ends (a negative price, a total price without units, a price in another currency than the cost), so they stay reported when a later syntax error drops the transaction. Like beancount, a syntax error drops the directive it is in and parsing resumes at the next line in column 1, or, as Bison retries each token after the error, at an earlier token that can start a declaration (a date, `option`, `include`, `plugin`, `pushtag`, `poptag`, `pushmeta`, `popmeta`): the one that raised the error, one later on its line, or one on an indented line: `Parse` returns the partial AST with a `ParseErrors` listing each one (and, in `AST.DroppedAmounts`, the amounts the dropped directives read before their error, which the ledger's display context counts, as beancount's parser feeds its display context with each amount it reads; the loader merges them across includes), and, as beancount's lexer reports every invalid token, each invalid token the recovery skips (one beancount's grammar alone rejects, such as a lone sign or an unmatched parenthesis, is not reported; a one-letter key such as `a:` is invalid). Like beancount's Bison parser, a grammar error is reported only once three tokens have been shifted since the last error, reported or not (`Parser.shiftedSince`: a line break and an indent count as tokens, a comment does not); an invalid token is always reported. Like beancount's lexer, a number is unsigned and a sign, a parenthesis and each of `+ - * /` are tokens of their own (a slash starting a currency, `/ESZ24`, is the currency), so a date or an invalid number inside an expression is lexed and reported as anywhere else; the parser reads beancount's `number_expr` from those tokens on one line (`parseNumberExpr`), a number with at most one sign written right before it keeping its text and any other expression evaluated in Python's decimal arithmetic. Like beancount's lexer, a date is four or more digits, then twice a `-` or `/` and digits, each part read as a number (`ast.DateLiteralLen`): `2020-1-2` and `2020/01-02` are dates, also as a cost's date or a metadata value, and one naming no day (`2020-13-01`) is an invalid token. Like beancount's lexer, the lexer fails on no input: a comment may hold any bytes, a string holding invalid UTF-8 is an error on the line the string ends on, and invalid UTF-8 or a control character elsewhere is an invalid token up to the next whitespace. Like beancount's catch-all rule, any invalid token runs to the next whitespace, a quote in it included (`invalidToken`); a quote opens a string only when its closing quote is found before a backslash ending a line (`closingQuoteAhead`), and a lowercase word that is no keyword or key lexes as the keyword starting it, if any, then an invalid token (`closed` is `close`, `d`). An invalid token starting the line right after a dated directive drops that directive, as Bison discards it while it waits to see whether the directive goes on; a blank or comment line between keeps it. A dated directive's header, a posting and an undated line (`option`, `plugin`, `include`, …) end at their line (`finishHeader` checks the token lines, since tokens own their newline): one continued on the next line, or metadata on its own line, is a syntax error, since beancount has no inline metadata. A blank or whitespace-only line ends a directive's body, so an indented line after one is a syntax error, as in beancount. Like beancount's INDENT, a line's leading whitespace is an indent only when it is spaces and tabs alone (`Parser.indented`, never `Column > 1`): a lone `\r` in it makes the line start in column 1. A string spanning lines moves that end to the line it closes on, where a comment is the inline comment; the parser finds that line with the lexer's own line count (`Parser.endLine`, `ast.CountLineBreaks`), which, like beancount's, breaks lines only at `\n` (`\r\n` included) and reads a lone `\r` as whitespace; `ast.SplitSourceLines` splits source text the same way for every reader of positions.

**Lexer newline ownership**: every content-bearing token (including COMMENT) consumes its trailing newline; NEWLINE tokens stand only for blank lines, emitted solely by `scanNextToken()`. `parseComment` strips the newline from the comment's content. Consistent ownership keeps the formatter idempotent around consecutive blank lines and comments.
