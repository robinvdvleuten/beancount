# `query`

`Run` is the interface: BQL text, a `Context` (the Ledger, whose options it reads, and the processed tree, both of which Run requires), a `Format` and numberify in; beanquery's bytes out (nothing for an empty text result, or for a text with no statement, which its shell skips: an empty one, or one opening with `;` or `(`). For a statement that does not parse or compile, or fails while it runs (an invalid regular expression or `subst()` replacement, which reads its replacement as Python's `re.sub` does (`query/template.go`), an integer overflow, a LIMIT beyond int64: `fail` panics with an `evalError` that `Run` recovers), `Run` writes nothing and returns an `*Error` with beanquery's message. `Error.Report` renders it as beanquery's interactive shell prints it: `error: ` and the message, the statement's lines up to the error's node behind `| `, and a caret under each character of the node (its `bql` span). A parse error is `syntax error` with one caret. An error beanquery raises without a node is the `error: ` line alone (KNOWN_GAPS.md). The CLI prints the report on stderr and exits 1; the web API returns it as output. `Run`, `Context`, `Format` and `Error` are the whole exported API; the stages behind it are unexported, and the package's own tests (all `package query`) reach them directly. Inside, parse → compile → execute → render: compiler resolves names and types with beanquery-parity error messages (a function by its name as written: the parser lowercases an unquoted one and keeps a quoted one; a double-quoted string (`bql.Str.DoubleQuoted`) as the column of the current table its value names, like beanquery's `_constant`, GROUP BY and ORDER BY matching it to that column's target through `exprKey`), and type-checks operators against `operators` (`query/operators.go`, beanquery's `OPERATORS`): an operand pair must match a signature exactly, after an untyped (object) operand is cast to the other's type (`casts`, beanquery's `types.MAP`); AND, OR, IN and NOT IN take any types (`untypedOperators`); BETWEEN's three operands must all be numbers, dates or strings (`betweenGroups`); NOT and unary minus look up `unaryOperators`, and a function call its overloads in `functions`, like beanquery's `function_lookup` (`lookupSignature`): each combination of the arguments' bases in turn, a bool's being bool then int, as Python's bool subclasses int, so a bool overload wins and an int one takes a bool as its int value (`asBase`); a typed operator on a NULL operand gives NULL; executor reads `Context.AST` (interpolated amounts) read-only and maps `Ledger.BookedPositions` to its positions for the position, cost and weight columns rather than re-deriving booking (FROM's summarization records the positions of the postings it creates); the `meta` columns are Python dicts built from a directive's or a posting's position and metadata (`query/meta.go`: filename, lineno, the metadata, and a posting's `__automatic__` when Booking interpolated one of its numbers, `ast.Posting.Automatic`), the only values a subscript takes; `entry` is beanquery's Transaction structure, its attributes in `attributes.go`, and printed as Python's repr of it from `Ledger.BookedPositions`; a SELECT reads a Table, an `environment` (`query/env.go`: its columns, the columns `SELECT *` expands to, and its rows), which its other clauses compile against: `postings` unless its FROM names another, `entries`, the Empty table (`#`), or one of beanquery's Tables of directives in `query/tables.go` (`transactions`, `prices`, `events`, `notes`, `documents`, `balances`, one row per directive of a kind, `commodities`, one per currency, and `accounts`, one per account opened or closed, whose `open` and `close` structures hold the `*ast.Open` and `*ast.Close`; a note's and a document's tags and links are `tFrozenset`, beanquery's raw `frozenset` type, which no function takes; a row a directive does not make up alone carries the rest as its `evalRow.Record`); `tables` holds them by name; like beanquery's `_compile_from`, a Table reference names a Table, and so does a FROM filter that is a lone name of one but not of a postings column, OPEN, CLOSE and CLEAR after it ignored; `meta()`, `entry_meta()`, `any_meta()` and `has_account()` compile as beanquery rewrites them, through the current Table's columns (`columnRewrites`), so they fail on a Table without them; SELECT (which BALANCES and JOURNAL desugar to) and PRINT share one FROM compile (`compileFrom`) and its OPEN, CLOSE and CLEAR transforms; like beanquery, a SELECT's FROM expression compiles over the postings table and joins WHERE as one filter on posting rows (`EvalAnd([c_from_expr, c_where])`), while PRINT's compiles over entries and keeps directives (`compiledFrom.entries`); PRINT hands what its FROM reads to the printer with `Ledger.BookedPositions`; HAVING compiles to a hidden aggregate target; like beanquery, a grouped query's targets outside the group key (HAVING's, an ORDER BY expression's) read their non-aggregate parts from the last scanned row; PIVOT BY reshapes the executed table after ORDER BY and LIMIT (`table.pivot`, beanquery's `EvalPivot`); ORDER BY, `min()`, `max()` and PIVOT BY order values as Python orders beancount's (`order.go`: `Position.sortkey` through `ledger.SortKey`, the one implementation, which also orders the ledger's inventories and residuals, amounts by currency, inventories by sorted positions, sets by inclusion, lists (list constants and `other_accounts`, a set-typed column holding a sorted `listValue`) element by element); the executor evaluates a row's targets where WHERE keeps it, and `balance` is lazy (`evalRow.balanceValue`), as in beanquery; numberify splits amount columns before either format renders; renderers reproduce beanquery's per-type layout byte-for-byte, quantizing amounts with `Ledger.DisplayContext` (source precisions, fixed by `display_precision`).
